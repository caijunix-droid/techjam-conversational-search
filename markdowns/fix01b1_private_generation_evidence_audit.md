## 2. Findings, classified

### 2.1 ORGANIZER-DOCUMENTED — the generation methodology is stated generically, not scoped to "public only"

`docs/competition_specification.md` (tracked, introduced in the original organizer
commit `2a6cc8e "Publish conversational search challenge"`, before any team work — `git
log` confirms this is the unmodified organizer publish, not team-authored), under
**Objective**:

> "The hidden target is based on a real purchase record from Amazon Reviews 2023.
> Customer messages are simulated from a hidden intent card derived from product
> metadata; the source dataset does not contain real shopping conversations."

This sentence describes the competition's customer-message generation mechanism in
general terms. It is not qualified as "for the public set only," and it appears in the
document that governs the whole competition (both splits), not in a document scoped to
local development.

The same document, under **Official Data**:

> "The public set has 200 labeled development sessions. The organizer keeps 800 sessions
> private. **Private intent cards**, ground truth, and simulator state are never sent to
> the participant Agent."
>
> "Both splits use the same fixed scenario mix: 40% Buying / 40% Browsing / 15% Intent
> Override / 5% Boundary."

"Private intent cards" is the same named artifact ("intent card") used for the public
mechanism, applied explicitly to the private set. "Both splits use the same fixed
scenario mix" is an explicit organizer statement that the two splits are not generated by
independently-designed processes with only coincidentally similar proportions — they
share a specification.

**Classification: ORGANIZER-DOCUMENTED.** This is a direct textual statement from an
organizer-authored, tracked, competition-governing document — not an inference drawn
from observing public-set behavior.

### 2.2 ORGANIZER-DOCUMENTED — the organizer's own slides describe one shared pipeline for both splits

Slide 7, "A reproducible pipeline creates the public and private sets" (literal bullets,
not the file's own "Digest" section):

> - Start from the official Clothing 5-core leave-last-out split.
> - Join targets and visible history to the frozen catalog.
> - Require usable pre-target catalog history.
> - Select distinct users and target products deterministically.
> - **Build anonymous profiles and organizer-only intent cards.**
> - Split public/private by user and target, then freeze checksums.
>
> Pipeline scale: `2,524,981 official leave-last-out records → 10,187 eligible
> catalog-joined records → 1,406 distinct candidate targets → 200 public + 800 private
> sessions + 50,000 frozen products`

The critical structural detail: **intent-card construction ("Build anonymous profiles
and organizer-only intent cards") is a pipeline step that happens before the
public/private split** ("Split public/private by user and target"), not two independent
processes that happen to produce similar-looking output. The pipeline scale line shows
the same funnel producing both the 200 public and 800 private sessions in one pass.

Slide 8, "Private labels stay private" (literal bullets):

> ORGANIZER KEEPS PRIVATE: 800 target `parent_asin` labels · **hidden intent cards** ·
> simulator state

Again, "intent cards" — the same term, applied to the private bucket specifically.

**Classification: ORGANIZER-DOCUMENTED.** Directly quoted organizer slide content (not
the digest author's commentary), corroborating §2.1 from an independent organizer source
(a slide deck) rather than only the specification document.

### 2.3 UNKNOWN — whether the private harness runs the identical `intent_card()` code path

`evaluator/local_evaluator.py` is described in this repo's own `README.md` file table as
the **"public-set simulator and scorer"** — i.e., participant-facing tooling for local
development, not asserted anywhere to be the literal code the organizer runs for final
private judging. Its `intent_card()`/`behavior_for()`/`customer_reply()` functions are
one concrete, inspectable implementation of "derive customer language from the target's
own metadata" (confirmed in the earlier safety-boundary audit:
`intent_card()` reads `product.get("features")`/`.get("details")`/title/price directly
from the target's own catalog row — `evaluator/local_evaluator.py:52-71`).

Whether the organizer's actual private-evaluation harness (in the missing
`organizer/` files) executes this exact function, a variant of it, or a differently
coded but methodologically equivalent generator, **is not established by anything
available in this repository or the slide deck**. The organizer-only files that would
answer this directly are confirmed absent by design (§1).

**Classification: UNKNOWN** (code-identity level). This is distinct from — and does not
undermine — the ORGANIZER-DOCUMENTED methodology-level finding in §2.1/§2.2: the
organizer has stated, in two independent tracked/officially-sourced documents, that one
shared pipeline with the same "intent card derived from product metadata" mechanism
produces both splits. What is not verified is whether that shared pipeline's actual
source code is byte-identical to the specific `intent_card()` function participants can
read — only that it is described as the same conceptual mechanism, applied before the
split.

### 2.4 INFERENCE (explicitly labeled by its own source, not organizer rule) — a caution about overfitting to public-set properties

The slides digest's own interpretive section 17 ("Hackathon Priority Order Derived from
the Slides") includes, as item 8: *"Tune against the 200 public sessions without
overfitting to public targets/users."* Per that document's own header disclaimer (§1
above), this is the digest author's engineering interpretation, not a verbatim organizer
statement, and is labeled **INFERENCE** here accordingly — included because it is a
directionally relevant caution, not because it carries organizer authority.

### 2.5 VERIFIED (background, not directly load-bearing for the B1 question)

From the same tracked/slide sources: 50,000 frozen catalog products; 200 public / 800
private / 1,000 total sessions; 1,406 distinct candidate targets across both splits; 0
public/private user overlap; 0 public/private target overlap; identical 40/40/15/5
Buying/Browsing/Intent-Override/Boundary scenario mix on both splits. These are
consistent across `docs/competition_specification.md`, `README.md`, and the slide deck,
with no contradiction found between sources.

## 3. Answer to the narrow question posed by the review

> "Do we have evidence that private-session customer constraints are also derived from
> the target product's catalog metadata in a structurally similar way?"

**Yes, at the methodology level, from two independent organizer sources** —
`docs/competition_specification.md` (a tracked, organizer-authored, competition-governing
document, stating the "intent card derived from product metadata" mechanism generically,
not scoped to public-only, and explicitly naming "private intent cards" as the same
artifact) and the organizer's own briefing slides (Slide 7's literal pipeline bullets,
showing intent-card construction as a single step applied before the public/private
split, not two independently-authored generators).

**No, at the exact-code level** — this repository does not contain the organizer's
private-evaluation harness, so whether it runs the identical Python implementation
found in `evaluator/local_evaluator.py`'s `intent_card()` is unverified and unverifiable
from available material.

This is explicitly **not** the reasoning the review warned against ("do not infer
private generation merely because public generation works that way" — i.e., do not
extrapolate from observed public-set statistics alone). The evidence here is different in
kind: it is the organizer directly stating, in writing, in two separate documents, that
one shared pipeline with a described mechanism produces both splits — not an
extrapolation from the 140/146 public statistic itself.

## 4. Where this leaves the review's decision tree

The review's own §11 laid out three branches. The evidence found here matches branch one:

> "If organizer evidence establishes that private sessions follow substantially the same
> target-derived construction: B1 confidence rises materially. Likely verdict: KEEP /

if methodologically the same, differs enough in implementation detail (e.g., different
regexes, different truncation, different candidate-string selection than
`evaluator/local_evaluator.py`'s specific `intent_card()`) to change the target-active-match
rate materially on the 800 private sessions. Nothing available narrows that residual
further.
